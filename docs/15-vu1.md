# VU1: the 3D models

Session 7 gave the runtime VU1, behind a full VIF1. The character select
shows its officers: Zhao Yun lit and textured under the spotlight, the
others in the dark around him, at 50 frames a second. The attract mode's
battle draws its walls, trees, ground and soldiers, but not yet at the
console's speed: one field in four or five the game finds its lists
unfinished and resets the GS (below).

```sh
# the character select
build/recomp-build/ps2run.exe "build/image/Dynasty Warriors 2 (Europe).cue" \
    --headless --seconds 42 --press 8:START,10:START,12:START,14:START,16:START,18:START,20:START,22:START,28:CROSS \
    --shot 41 --shot-dir build/shots
# VU1's microcode, data memory and registers at each program's first start
PS2KIT_VU1_DUMP=build/vu1 build/recomp-build/ps2run.exe ...
python -m ps2kit.vu build/vu1/micro_0.bin                     # disassembly
build/recomp-build/vubench.exe build/vu1 0 0010 --repeat 20000 --out before.bin   # time a program, write its results
```

## VIF1

`ps2kit/runtime/vif1.cpp` carries out the codes DMA channel 1 brings:
UNPACK in every format (with STCYCL's skipping and filling writes, STMASK,
STMOD, STROW, STCOL, FLG and TOPS), OFFSET and BASE (the double buffer:
TOPS flips between BASE and BASE + OFFSET at each start, OFFSET clears DBF),
ITOP, MSCAL, MSCALF and MSCNT (TOP and ITOP taken at the start), MPG into
VU1's 16 KB micro memory, DIRECT and DIRECTHL into GIF path 2. The lanes a
format leaves undefined (V2's z and w, V3's w) and the filling write's
data are written as PCSX2 writes them; DW2 masks them or does not use them.

What DW2 sends, from the census: 13 MPGs at start-up (13 176 bytes); on the
character select UNPACK V4-32, MSCAL to four entries (0x0000 setup, 0x0010
the skinned models, 0x0050 the rigid parts, 0x0080 the matrices), OFFSET and
BASE; in a battle also MSCNT (about 100 000 a second), UNPACK S-32, S-8,
V2-32, V3-32, V4-8, and a new MPG about once a frame.

## VU1 and one interpreter for both units

`ps2kit/runtime/vu.cpp` is the micro-mode interpreter VU0 and VU1 share
(VU0 keeps its VIF0 in `vu0.cpp`). VU0's interpreter only checked that a
program read Q and the flags late enough; VU1's code is software-pipelined
(DW2's rigid-part loop reads the MAC flags exactly four pairs after the
SUBA that set them, with two newer FMAC results in flight), so the
pipelines are modelled now: VF registers ready four cycles after their
instruction, with stalls on the lanes read; the MAC, status and clip flags
written four cycles after; Q seven (DIV, SQRT) or thirteen (RSQRT) cycles
after, the old Q seen until then; the EFU's P after its latency (ESIN 29,
EATAN 54, ...); ILW four cycles for a branch. The latencies are the VU
manual's, the stall rules PCSX2's interpreter's. VU0's trigonometry library
gives the same results as before (tools/vu0check.py: within 2.2e-5 of libm,
the polynomials' own error).

XGKICK hands the GIF packet at its address (to the tag with EOP) to GIF
path 1. VIF1 and VU1 run on a thread of their own, ahead of the GS's:
before, VU1 ran inside the game's vblank handler (which sends the frame's
lists), took more than a field, and the game's main thread never ran: the
character select's fade-in stopped at its first step.

Speed: pairs are decoded once per micro memory, a quick test skips the
stall check when no register read is in flight, and the FMAC arithmetic
runs with the host's DAZ and FTZ set (a denormal operand counts as zero,
a denormal result becomes one, as the FPU model's clamp makes them; only an
operand with exponent 255 needs the clamp first). Each step was checked with
`vubench`: the data memory and registers after a recorded start equal,
byte for byte, to the first interpreter's. From 22 to 50-57 million pairs a
second (the character select's programs; a battle program).

## vf30: written by the EE, through VU0

The character select's models first came out black. The setup program
(0x0000) computes the fog factor of every vertex as vf30.w / depth +
vf30.z, clamped to 0..255; FOGCOL is black. No VU1 program the game runs
before or on the character select writes vf30 (the battle's world setup
loads it from data memory), and VU1 starts with zeros, so the fog factor
was 0 and the models were drawn in the fog colour. Forcing vf30 to
(0, 0, 255, 0) (`PS2KIT_VU1_VF="30:0,0,255,0"`) showed Zhao Yun lit and
textured. Session 7 guessed that the BIOS's start-up animation left the value
in VU1; in PCSX2 a fast boot and a full BIOS boot show the same lit officers
(the user checked, session 8), so the game sets it itself.

It does, from the EE. `SetFogOff` (mdlview.c, 0x210110) builds the vector
(0, 0, 255.0, 0) and stores it with a macro-mode `vsqi` to the quadword
address in a float at gp - 0x7D8C: 1054.0, that is 0x41E. VU0's data
memory is 4 KB, but VU0 addresses VU1's registers from byte 0x4000 (vf0 to
vf31, then the VI registers a quadword each from 0x4200); 0x41E is VU1's
vf30. The runtime wrapped every VU0 address to 4 KB, so the store landed in
VU0's own memory at 0x1E0. Now `vu0_q` (macro mode) and the micro-mode
interpreter send addresses with bit 0x400 to `ee_vu0_vu1reg`, which hands
out VU1's VF register (the VI half stops with a message: not used here). The
character select shows its officers lit with no preset; `PS2KIT_VU1_VF`
stays for experiments.

## The GS's CLUT buffer

A profile of a battle field (`gsreplay --profile`) showed the GS reading
its CLUT from local memory for every triangle (256 entries, each through
the generic addressing). The GS loads a CLUT into its own buffer when TEX0
or TEX2 is written, as CLD says (1 always; 2 and 3 setting CBP0 or CBP1; 4
and 5 only when CBP differs from them), stored from entry CSA * 16 and read
back from there; the runtime does the same now, and the fast rasteriser
keeps the converted table until the buffer, the CLUT format, CSA or TEXA
change. A battle field went from 15 ms to 8.5 ms (with a faster bilinear
rounding), the fast rasteriser still equal to the reference on 40 fields.
GS recordings carry the buffer (state version 2; older recordings are
refused).

## Where the battle stops: the GS reset

DW2's vblank handler (`main_callback`, decompiled with
`ps2kit/ghidra/Decomp.java`) asks `sceGsSyncPath(1, 0)` whether DMA channels
1 and 2 are still busy; if so it takes the GS for hung and resets it
(`sceDevVif1Reset`, `sceGsResetGraph`), and that field shows a PCRTC set up
as after a reset (PMODE 0xBE66, a 32-bit display buffer: green). In the
attract-mode battle the frame's lists take VIF1 and the GS together up to
about 20 ms (the heartbeat now prints each channel's start-to-end time), so
one field in four or five is lost. Holding the vertical blank until the
channels end was tried and made things worse (the game then sent about
four times the work per blank); it was taken out. What is left is speed:
the GS on several threads, and VU1 faster still (a translator of its
microcode to C++ would be the large step).

## Tools added

* `PS2KIT_VU1_DUMP=dir`: micro memory, and at each program's first start
  its data memory and registers.
* `vubench DIR N ADDR`: one recorded start, timed, its results written
  (`--out`) to compare two builds byte for byte; `--profile`.
* `PS2KIT_VU1_VF=N:x,y,z,w[;...]`: VF registers VU1 starts with.
* `PS2KIT_VU1_OFF=1`: VU1 runs nothing (debugging).
* `PS2KIT_VIF1_SYNC=1`: VIF1 on the caller's thread.
* `PS2KIT_PROFILE_STACKS=1`, `PS2KIT_PROFILE_FROM=S`: the profiler counts
  whole guest call chains, from S seconds on.
* `gsreplay --vram OUT` and `python -m ps2kit.gsmem --vram`: local memory
  after a replay, and any buffer or texture in it as a PNG.
* `ps2kit/ghidra/Decomp.java`: functions decompiled by name into one file.
